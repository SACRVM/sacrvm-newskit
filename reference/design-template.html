Newskit

A sister kit to SACRVM APPKIT for publishing long-form, source-backed articles. It wears appkit's own look — the news feeling comes from structure and hierarchy, not a separate skin.

Drafted 24 Aug 2026 Reviewed by Fable + Grok Zero build Appkit-native look
Part 01
The idea

Appkit, extended for reading

Newskit does not invent a new visual language. It is appkit — same tokens, same fonts, same surfaces — specialised for the one job appkit isn't shaped for: a long article, read top to bottom.

SACRVM APPKIT is built for operating software: a workspace shell, controls, floating windows. An article is a different shape of page — one column, minutes of reading, a clear top-to-bottom hierarchy. Newskit keeps appkit's identity and adds the layer that shape needs.

Inherited from appkit, unchanged — the machinery AND the look: the seed→derived theming engine (--bg, --surface, --accent, light / dark / auto), Inter (reading) + Outfit (labels), rounded surfaces and hairline borders, the sac.* namespace and component pattern, and the whole delivery model — autark vendoring, GitHub-Action ZIP, versioned VERSION.

Added by newskit: a reading-optimised layout with a persistent left chapter rail (a ToC that tracks the current section — this page has one), one condensed display face for headlines (Oswald — the reference's signature, the part you singled out), a small set of article primitives, and — the real point — sources and provenance as first-class citizens, because that is what a researched article stands on. The reference article supplies the structure and the headline treatment: masthead, layered sections, entry cards, a sources block per claim, pull-quotes, a method note. Rendered in appkit's palette, that reads as news without becoming a magazine pastiche.

RelationshipA separate repo, sacrvm-newskit, that vendors appkit exactly like any consumer app (the release ZIP's kit/ dropped in verbatim, linked locally). Newskit's reading layer sits beside it and consumes its tokens directly — so the two never diverge in look, and appkit's core stays lean (the parked "md-editor add-on" precedent: specialisation lives outside core).

Part 02
Locked

The decisions

Three forks you chose, plus three principles I set. These bound everything below.

Authoring — hand-written HTML with kit elements

Your call · 24 Aug 2026

An article is an HTML file that uses newskit's custom elements and classes directly. No render layer, no markdown step — keeps the no-build conviction and gives full layout control. An AI author emits the HTML; the kit supplies a documented page skeleton and a fixed component vocabulary so the output stays consistent.

Identity — appkit's look, tuned for a news feeling

Your call (corrected) · 24 Aug 2026

Not a warm-paper magazine and not a serif print skin — appkit: the same seeds, rounded surfaces, hairline rules, --accent, Inter for reading and Outfit for labels. The one deliberate nod to the reference is its headlines — big, condensed, uppercase (Oswald) — the part you called cool. They carry the news feeling together with the layout and hierarchy, without touching appkit's palette or body text. This page is that look.

Consequence for the design rulesBecause we stay in appkit's rounded world, the "no thick colored border on a rounded surface" rule applies in full. Entry cards get their accent from the eyebrow colour and a subtle accent-tint block (like this one), never a 3px colored stripe. The one thick rule we do keep is neutral and flat: the 2px masthead underline.

Scope — articles + a hub + article metadata

Your call · 24 Aug 2026

Core is: the reading layout & components, a hub (index of article cards), and per-article metadata — OpenGraph / Twitter / schema.org Article plus reading-time. A feed (RSS/Atom) and tags/series are designed-for but documented as a later extension, not built in v1.

Principles I set (veto any)

Assumed, pending your nod

Credibility is the kit's jobNewskit owns the trust primitives — sources, provenance, a method/disclosure block, the claim↔evidence pairing. That is what makes an AI-researched article defensible, so it belongs in the shared kit.

The AI pipeline is separateResearching and writing is a different project (a tool, later). Newskit renders and structures; it does not generate.

Prefix stays sac-*One component family across both kits, so appkit and newskit read as one ecosystem.

The editorial layer

Fonts

Three roles: Oswald (condensed, uppercase, 500/600 only) for headlines — the reference's signature; Inter for reading; Outfit for labels. Only Oswald is new; both others are appkit's. Self-hosted & subset like the others, no CDN.

Tokens

Appkit's seeds and derived tokens verbatim: --bg, --tile, --accent, --border, radii. A retheme of appkit rethemes newskit.

Reading layer

What's new: a ~40rem prose measure (~68ch), body on --text (not muted), an article type scale, the section/record/sources rhythm.

Theming

light / dark / auto for free — same engine, same data-theme. Contrast re-solved per scheme so no tier drops below AA.

Hard rules from the design review (Fable + Grok)Body copy is primary --text, muted is for standfirst/notes/origins only. Prose measure ≤ ~40rem — the widest lines must not be the dense evidence cards. Micro-type floor 0.7rem; every text tier ≥ AA in both schemes (no shared mix ratio across light/dark). One display moment per viewport — analytical prose sits on bare ground between record tiles, so the middle never reads as a settings screen. The masthead's 2px rule is neutral, not colored.

Part 04
Publishing

The hub & the trust layer

What turns a folder of article pages into a publication — and the review's verdict: this is the real design job.

The hub is a reusable index: a front page of article cards (kicker, title, standfirst, dateline, reading-time, source count), built with the kit and appkit's tile look. Adding an article is adding a page and a card — no CMS, no database.

Article metadata ships as a documented <head> block: OpenGraph + Twitter cards for link previews, schema.org Article for search, a computed reading-time.

The trust layer is the differentiator — and both reviewers said it must be designed, not merely structural. It is four visible primitives, shown in the specimen above: inline sac-cite markers so a claim carries its evidence; sac-sources as scannable chips (domain · accessed date) so "this claim has three sources" reads at a glance; a sac-provenance strip under the title; and a method/disclosure callout with its own warm signature. The reference lives this — every claim resolves to a link, including claims it rates unsupported. That honesty is a feature of the format, and the kit makes it the path of least resistance. No "AI purple/glow" — trust reads as timestamps, structure and evidence density, not decoration.

Part 05
Writing one

The article, as a file

Hand-authored HTML — the shape an author (human or AI) fills in.

Every article is one self-contained page: a documented <head> (metadata), links to the vendored appkit + newskit.css, then the body assembled from the primitives. A skeleton and a filled reference (the demo) ship in the repo, copy-to-start.

Part 06
Shipping

Repo, build, release

Same discipline as appkit — because it is the same discipline.

ConcernHow

BuildNone. Plain files, npx serve ., F5. Packaging only server-side in the release Action.
FontsSelf-host + subset Oswald into newskit/fonts/ exactly like appkit does Inter/Outfit — the Google CDN link is scratch-only.

Part 07
Order

Build order

Smallest first; each phase is usable on its own. The review moved the cite/sources UI up into the core — it is the thesis, not a garnish.

  1. Reading layer

    newskit.css on appkit's tokens: the ~40rem measure, prose rhythm, article type scale, per-scheme AA contrast. Proves the look in light/dark.

  2. Core primitives + the trust layer

    sac-article, sac-masthead, sac-section-head, sac-record, sac-sources (chips), sac-cite, sac-provenance, sac-callout (method signature), sac-pullquote, sac-figure, sac-colophon.

  3. The demo article

    The reference piece re-typeset with the primitives — end-to-end proof and copy-to-start reference.

  4. Styleguide

    Every primitive live, with attribute/slot tables — built with the kit, appkit-style.

  5. Hub + metadata

    Publication index, OG/schema.org Article, reading-time, source counts on cards.

  6. Release plumbing

    The Action, VERSION, self-hosted fonts, CONSUMING.md, the two-kit vendoring recipe.

  7. Documented extensions

    Feed (RSS/Atom), tags/series, source access-dates — designed-for now, built when wanted.

What newskit is not

No build step, ever — plain files and F5, like appkit. No CMS or backend; a publication is static pages. No markdown parser (you chose hand-HTML). No AI-authoring inside the kit — that seam stays clean. No feed or tag system in v1 — designed-for, deferred. And no separate skin: newskit shares appkit's palette and body type; the news feeling comes from structure and the condensed headlines, not from a different colour world.
